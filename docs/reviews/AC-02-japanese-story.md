担当：quest_designer。対象は main `f22855d9f5779fa2c15222175537369367714ff0`、2026-10-26の静的レビュー。開始時のHEAD一致と製品ファイルの差分なしを確認した。編集は本書のみ。製品実装、ブラウザー操作、人間のプレイ観察は行っていない。

## 結論と適用範囲

「だれが、何に困っているか」「プレイヤーはどの画面で何をするか」「何を確認してだれへ知らせるか」が、荷物・道・札・窓口などの比喩だけになっている箇所がある。とくに序章の「手帳を届ける」は、受け取る報酬と報告する内容を取り違えている。DX-01の案内は、メールを届ける主体が分かりにくい。

以下は差し替え可能な文案18件。**先行修正**は文章と実操作の食い違い、**説明改善**は目的を読み取りにくくする具体的な省略を扱う。利用者が実際に迷ったと断定するものではない。好みの問題だけで、無関係な実装の完了を止める提案ではない。

依頼人名・操作の順序・金額・章選択・未受講の扱い・期限・固定XP・保存・報酬IDを変更しない。NPCの会話は「〜なんだ」「〜してくれない？」など短い口調を残す。章の風景や敵名の比喩は残し、目的を説明する本文に具体的な対象と動詞を足す。

`adventureCatalog` の incident/goal は `questBrief()` を経て受注画面（app.js:85–86）、室内会話（:96）、ナレーション（lesson-guide.js:130）、スマホ見出し（app.js:148）へ出る。同じ文を画面ごとに増やすより、ここを先に直すと説明がそろう。

- 根拠：帆が混ぜるという主語と「風の揺れ方」という対象がかみ合っていない。ロング／ショート・倍率・損益を学ぶ用事だと読めない。
- 修正文（incident）：「ソラは、ロングとショート、倍率の違いで、損益がどう変わるか調べたいんだ。」
- 修正文（goal）：「向きと倍率を選んで注文し、建玉を全決済して結果を記録しよう。」
- 修正文（区切り名）：「選んだ向きと倍率」「値動き後の含み損益」
- 修正文（完了反応）：「全決済して、建玉の残量ゼロを確かめたね！ 別条件の確認課題では、向きや倍率を変えて損益を比べられるよ。」
- 受入条件：一回の本編だけで複数条件を比較済みと扱わない。方向・倍率の有効選択、利益に依存しない報酬、別条件確認の扱いを保つ。帆の絵は物語の結果に残せる。

### AC02-17 「いまの作戦」に名詞だけが出る

- 区分：説明改善。ui-adventure.js:38、adventure.js:209。表示元の選択も含む提案。
- 現文：「いまの作戦：言葉のかけら」「いまの作戦：練習の名前札」など。`currentStage.title` が `nextGoal` より先に使われる。
- 根拠：区切り名は思い出すための題名で、次の操作を指示する文ではない。`getAdventure()` は実際の `step.instruction` を `nextGoal` に入れているため、既存の目的データを使える。app.js:166で本体からこの場面を描画する。
- 修正文：「次の操作：メールの合言葉をコピーしよう。」など、現在工程に対応する文。区切り名を残すなら「この区切り：言葉のかけら」として別の役割を示す。
- 受入条件：場面の案内に対象と動詞がある。章や依頼を一括完了する案内にしない。進行や判定は変更せず、読み取り表示だけを具体化する。

### AC02-18 買った後の装備案内を、実際のボタン名に合わせる

- 区分：説明改善。rpg-ui.js:177、同:148。
- 現文：「買ったあとに『装備する』で身につけます。」
- 根拠：購入後に出る既存ボタン名は「この装備を身につける」。「装備する」という名のボタンはこの画面にない。操作先を固有名で案内するときの不一致で、口調の好みではない。
- 修正文：「買った後は『この装備を身につける』を押そう。身につけると強さに反映されるよ。」
- 受入条件：購入後の実際のボタン名と一致し、買うことと装備することを分けて説明する。価格・強さ・購入回数・装備処理は変えない。

## 横断してそろえる書き方

1. **依頼の冒頭は人を主語にする。**「鏡が確かめたがる」「時計が戻ったことにする」「帆が混ぜる」は敵や舞台の演出には使える。困りごとは「スイは申込情報が合わず困っている」「ソラは資金がいつ戻るか分からない」と書く。
2. **作戦文は対象と動詞を一組にする。**「条件・数量・照合・確定」だけを並べず、「受取カードと宛先を比べる」「元の建玉を選んで全決済する」と書く。段階名は短くてもよいが、操作指示の代わりにはしない。
3. **比喩は具体語に続ける。**「ネットワークという送り道」「HLPに預けた資金を、蔵の荷物として描く」の順なら対応が分かる。本文からネットワークや資金を消して、道や荷物だけにしない。
4. **結果の主体と対象を安定させる。**序章は一貫して「合言葉」。カードは出品→売却→発送→受取→入金。「登録メールを送る」と「サービスから確認メールが届く」を分ける。
5. **報告は物の配達と分ける。**手帳は受け取る報酬、合言葉の保存や受取明細の照合は知らせる結果。「結果を届ける」だけで済ませず、「ルカに、財布へ届いたことを話そう」とする。
6. **名詞の連結をほどく。**「申込済み設定」→「申込を終えた設定」、「処理費用用の資産」→「処理費用を払う資産」、「元本と利息受取」→「元本と利息を受け取る」。専門語は必要なものだけ残し、一度に説明を足しすぎない。
7. **ボタン・人名は表示先と一致させる。**説明でボタンを引用するときは実ラベルを使う。依頼人名は `brief.client` と一致させ、帰還文だけ別人にしない。

rooms.jsは部屋名・扉名・出口の短いラベルが中心で、今回の基準に当たる主要な主述の不一致は見つけなかった。酒場の固有名や敵名を日常語へ全面置換する提案はしない。ui-adventure.jsの長老の「次の旅の道しるべじゃ」など、操作説明の前後にある短い口調も残せる。
