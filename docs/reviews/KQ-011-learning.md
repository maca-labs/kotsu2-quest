## 重要指摘

### LR-01 / Blocker：序章の指示どおりの外側「町へ戻る」で完了しない

- **箇所**：`js/content-points.js:14`、`js/app.js:103`・`:108`。仕様：pointquest付録A PR-01-012、§12。
- **再現**：PR-01を011まで進める。012の「スマホ外の教材枠／町へ戻る」という指示に従い、冒険場面側の「町へ戻る」を押す。
- **期待**：012を一度達成し、町の完了会話へ戻り、手帳を受け取る。
- **実際（コード）**：外側ボタンは`nav('world')`のみ。012のSTEPを送らない。同名のスマホ内genericボタンがSTEPを送るが、その直後は町ではなく依頼完了パネルになる。
- **影響**：正しい位置の指示に従った人ほど未完了で町へ戻る。最初の報酬と「押すと結果が変わる」の因果が切れる。
- **修正案・再確認**：外側の該当操作を012の達成と町の完了会話に結び、内外の同名ボタンを別の意味にしない。外側操作だけで手帳・64基本XPが一度だけ成立し、再読込み・再会話で増えないことをブラウザーで確認する。

### LR-02 / Major：アプリ切替の練習で、切替前に元のアプリを表示する

- **箇所**：PR-01-007/008、P015/016の`appId`、`js/app.js:68`・`:92`、`js/phone-panels.js:35`〜`:39`。仕様：pointquest §7、付録A 007〜008、付録B P015〜016。
- **再現**：メール本文でコピーした直後のPR-01-007、またはP015を見る。下部のアプリ切替を押した後の008/P016を見る。
- **期待**：メール画面を保ったまま下部の切替を操作し、最近使ったアプリの一覧からメモ／入力中ブラウザーを選ぶ。アプリとブラウザー内タブの違いが見える。
- **実際（コード）**：007は`appId:memo`、P015は`appId:browser`。描画は現在の端末状態より次工程のappIdを優先する。008/P016も同じappIdで、実際の最近使った一覧ではなく「アプリ切替」という見出しとgeneric操作になる。
- **影響**：どこへ戻るために何を切り替えたのか、入力がどこに残ったのかを操作から学べない。
- **修正案・再確認**：現在アプリ・切替一覧・選ぶ対象を明示する。メール→切替一覧→元の入力欄を実操作でたどり、関係ないアプリへの寄り道後も同じ入力へ戻れることを確認する。画面到着だけで切替技能を一括付与しない。

### LR-03 / Major：開くべきメモや利用条件の実体がない

- **箇所**：PR-01-002、P008/P009、`js/phone-panels.js:84`〜`:92`、`js/content-points.js:557`以降の共通説明。仕様：pointquest §§6・7、付録A 002、付録B P008〜009。
- **再現**：002で「下方の今日の用事」を探す。P008を押した後、何に同意するのかP009で確認する。
- **期待**：メモの下方に今日の用事があり、開いた内容が見える。利用条件は架空サービスの短い本文を読んでから同意欄へ進む。
- **実際（コード）**：メモには依頼名・コピー状態・合言葉があるが、下方の用事の実体はない。002はgenericボタンで保存値のscrollPositionを400にする。P008/P009の本文は「短い条件の表示」「登録送信可能」という結果ラベルで、条件そのものではない。`panel:'form'`という文字列も条件本文になっていない。
- **影響**：読む対象を探す迷いと、内容を読まず確認欄を押す習慣につながる。移動・スクロール、内容との照合の技能証拠が弱い。
- **修正案・再確認**：実際のメモ本文・下方の用事・短い条件本文を用意する。スクロール位置だけで理解を認定せず、開いた用事に対応する後の操作で照合する。初回と別条件課題の両方で同じ実UIを使えることを確認する。

### LR-04 / Major：メールを探す前に、答えを共通の説明へ出している

- **箇所**：`js/content-points.js:557`〜`:558`の共通説明、`js/phone-panels.js:92`、`js/app.js:77`。仕様：pointquest §8の技能の証拠、§12、付録A/Bのメール→コピー→入力という因果。
- **再現**：PR-01-002のメモを見る。PO-01のP002〜P010で説明欄を見る。
- **期待**：用事の目的は先に分かる。合言葉・確認コードそのものは、届いたメールを開いた結果として得る。
- **実際（コード）**：PRの共通説明・メモに最初から「一歩ずつ」があり、POの共通説明にはメール到着前から246810がある。コピーの前提検証はあるため不正に完了できるという指摘ではない。
- **影響**：メールを見た結果として情報を手に入れた実感が弱く、コピーを行う理由を「順に押す決まり」と誤解しやすい。
- **修正案・再確認**：初回の練習カードと、メールから得る値を分ける。別条件の確認メールでも、現在のメールを開いて得たコードをコピー・貼り付けして認証し、元のコードやUI内の期待値を参照しないことを確認する。

### LR-05 / Major：現在の「方向・倍率」は自由に選べる練習ではない

- **箇所**：`js/content-crypto.js:455`、`js/engine.js:43`の`validateAction`。仕様：別冊§12の注文前の倍率操作。新しい自由選択の要望は元の検算固定例と区別する。
- **再現**：HY-PERP-S007でショート、S009で1倍または5倍を選ぶ。
- **期待（追加要望）**：選んだ方向・倍率に対応して建玉金額・数量・損益が変わり、その条件で確認・注文・決済できる。
- **実際（基準版）**：主ラボはロング・2倍の固定値。候補は見えるが、他の値は正解との不一致として止まる。別条件課題も固定1倍等の検算であり、利用者の自由選択ではない。
- **影響**：「自分で選ぶ」と「指定された値で検算する」の混同。倍率を変えても数量が固定のまま、などの後付け実装を招く。
- **修正案・再確認**：主ラボの固定検算を残すなら、その旨を明示し、自由練習は別snapshotにする。新規注文前の方向・倍率変更が同じ計算結果から表示され、保有後に倍率を触って既存数量が変わらないことを確認する。高倍率・利益でXPや熟練を増やさない。

## 最小の共通契約へ返す提案

1. 工程は「今いるapp/screen」「操作対象のcontrolId」「一つの操作」「結果predicate」「ヘルプ参照」を持つ。次工程のappIdで先回り描画せず、文言の正規表現で下部ナビの意味を推測しない。
2. `focus → 入力/候補 → 確認画面 → 確定 → 結果`を分ける。P005/P007のような「チップを押す」工程に、同名の第二送信を無説明で足さない。候補入力を補助にする場合は、入力後に何を押すかが一つ分かる文言にする。
3. 実画面の利用条件・メール・板・申請履歴を、到達した状態から表示する。現在値と見積り、処理中と受取、元手と評価額を区別し、確認対象を結果ラベルだけで代用しない。
4. 初回の固定例と、パラメータを変える自由練習、条件違い課題を別の保存状態・証拠へ。表示と判定で同じ金融計算を使う。
5. 間違いは現在の欄に理由と直し方を出し、正しい欄・入力・コピー・受注時計を保持する。戻る・通知・アプリ切替の合法な別経路でも、その状態の証拠で同じ工程を満たせるようにする。
6. 村人は現在の案件の直近の控え、長老オリベは過去の実完了工程の記録・意味・つまずきを案内する。途中案件は途中と明記。新機能の追加だけで未完了工程を記録庫へ載せず、閲覧から金融処理やXPを実行しない。この既存の役割分担を保つ。
