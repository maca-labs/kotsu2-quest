## 結論

地図へ毎回スクロールが必要な原因は、地図の前に常時ナビ・章見出し・長いミッション全文・宿のカード・相談や町の便りを積み、移動/読込み後にその先頭へ戻す構成にある。390×844で地図が画面外になることは親の公開ブラウザーでも再現した。

地図を主画面の先頭へ置き、常時ナビと説明全文を必要時に開く構成へ変えるのが妥当。地図だけ順序を変えても、3行64pxの十字キーと説明をすべて残すと短い画面を圧迫する。地図と十字キーを一つの主stageとして縦の予算を決め、メニューの開閉・Esc・フォーカス・戦闘復帰を同時に検証する必要がある。

## TQA-01 町の地図が第一画面に現れない — Major

- 仕様根拠: 町を歩き、村人へ話しかけて進むRPG。スマホでも主操作を見つけ、操作できること。
- 再現: 390×844、保存済みの町を読込み、または「町へ行く」/章選択で町へ移る。scrollY=0で地図と十字キーを探す。
- 期待: 町に戻ると地図・主人公・方向ボタンがすぐ見え、説明全文を読んでスクロールし直さず歩き始められる。
- コード上の実際: shellは7項目のナビを常時表示し、狭い幅ではwrapする。renderWorldViewはheading→story-mission全文→HP/宿カード→相談ボタン/町の便り→world-grid内の地図の順。nav、travelArea、enterChapterはscrollTo(0,0)でその先頭へ戻す。
- 親の公開ブラウザー実測: 390×844、scrollY=0、町を開いた直後のcanvas top=1217.421875 / height=231.109、world-controls top=1456.531 / height=280.187 CSS px。担当自身のブラウザー計測ではない。
- 影響: 地図の上端すら最初の画面にない。主操作へたどり着くたび縦に移動し、RPGの移動をすぐ始められない。
- 修正合格条件: 320×720 / 390×844の両方で、町への初回表示・再読込み・室内からの退室・別章からの帰還時、scrollY=0のまま主人公を含む地図と十字キー全5操作を表示し、実際に1歩→長押し→離すができる。細かな説明/案件/相談/宿への入口は残す。

## 縦方向の主因と最小の構成

|対象|現状の根拠|必要な調整|
|---|---|---|
|常時ナビ|shell内の7項目、760px以下でflex-wrap。全ボタン44px以上|閉じた状態は1個の「メニュー」入口。章/依頼/装備/記録/設定/世界の選択は開いた中へ残す|
|二重の見出し|topbar、page-heading、world-toolbarが並ぶ|町名と短い現在目標を圧縮して地図に添える。長い副題や飾り見出しを第一画面へ重ねない|
|ミッション全文|物語、指示、段階、主ボタン、ヒントが縦積み|現在目標1〜2行＋主行動は見える。全文と手順は「依頼の説明」等で読めるようにする|
|宿/相談/便り|地図より前のカードと複数ボタン|地図の後、メニュー、必要時の別表示へ。HPは短い数値で常時見せてもよい|
|地図|width:100%、25:18のcanvas|主人公・出口・人物が見える比率を維持。必要なら表示幅も一緒に縮める|
|十字キー|3×64px＋2×6px=204px。note/余白も追加|有効な押し面積を保ち、noteは短文または展開式へ。地図との間の大きなカードを置かない|
|移動後の表示|scrollTo(0,0)|先頭自体がゲームstageなら合理的。説明だけ先頭に残して自動スクロールする応急処置は、再読込みやfocus時の別経路を取りこぼす|

320px幅でcontent左右12pxなら地図の外幅は約296px。25:18比の地図自体は約200px程度、十字キー本体204pxと合わせて400px以上を使う。これはCSSからの概算であり、実際の位置/高さの計測ではない。上部を短いヘッダと目標に絞れば720pxでも配置を組めるが、枠・note・安全領域・長い町名まで含め、最終寸法はブラウザーで判定する。

画面に収めるためcanvasのheightだけを縮めたり、object-fit:containで余白を作ったりすると、既存のクリック座標変換が表示中の人物とずれる可能性がある。25:18を維持して縦横を一緒に変えるか、余白分を変換へ反映する。地図の拡大率は描画と入力の両方で一致させる。

## メニューの必要条件

以下は新しい閉じたメニューの修正合格条件であり、現行版に実装済みという主張ではない。

1. 「メニュー」の名前と開閉状態が分かる。入口と各項目は44px以上、短い画面でも閉じる入口が届く位置にある。
2. 開く際worldControls.stop()。閉じても長押しを勝手に再開しない。menuにpointer操作を吸われた後も次の移動が新しいpointerdownから始まる。
3. 既存#modalとは別のdialogを使う場合、canMove、walk、global keydown等の移動入口もmenu.open/任意のdialog[open]を考慮する。現状はmodal.openだけを見るため、別メニューの題名にfocusした状態の方向キーが背後の移動へ流れる恐れがある。
4. モーダル方式なら背後を操作不可にし、Tab/Shift+Tabがメニュー内を巡る。非モーダル方式ならそれに適したfocusと閉じ方を定義する。いずれもEscapeと明示的な「閉じる」を提供する。
5. Escape/閉じる後は生存するメニュー入口またはゲームの適切な位置へfocusを戻す。遷移でDOMを置換した場合、消えたボタンへ戻そうとしない。地図や入力の最下部へ突然スクロールさせない。
6. 会話/報酬/説明/動画と同時に二つのモーダルを開かない。既存modalのcloseイベントによる動画停止・説明からの復帰・pendingRewards処理を誤って発火/消失させない。
7. 戦闘中の設定閲覧は維持。町・章・装備などを選んでも既存nav/engineのactive戦闘制約を通し、combatへ戻れる。閉じるだけで逃走・回復・ターン消費を起こさない。
8. 開く/閉じる/説明の展開はuiの表示状態だけ。START/CHAPTER/STEP/REST、送金、XP、コイン、報酬、保存版/IDを追加変更しない。項目を選ぶ行為だけが既存の正式な操作入口へ進む。
9. 新しいメニューを描画するため全画面を再作成する場合、既存worldControls/operationGuideをdestroyしてリスナー/タイマー/Observerを残さない。現在のrenderの破棄契約を維持する。

## 親へ渡す最終検証ケース

- 320×720と390×844、町/室内/世界/洞窟、初回・再読込み・退室・章移動。地図/十字キーのrectとscrollY、横overflowを測る。
- 閉じたメニューで地図を1歩移動→長押し中にメニューを開く→閉じる/Escape→2秒放置。勝手に歩かず、次の新しいタップで歩ける。
- Tab→メニュー→項目→閉じるのfocus経路、タイトルへfocus中の方向キー、閉じた後の表示位置。
- 戦闘途中→メニュー→設定→閉じる/町等→combat。battleId/turn/HPを保持。別画面から戻れない状態を作らない。
- コピー直前・入力途中のメニュー開閉とJSON再開。draft/clipboard/工程/XP/金融台帳は変えず、必要な確認を飛ばさない。
- 長い章名、町の便りあり、進捗/報告待ち、文字拡大、狭い縦画面でも主操作が届く。本文は必要時に普通にスクロールできる。
