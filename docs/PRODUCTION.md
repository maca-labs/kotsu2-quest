# 制作チームの設計と運用

制作運用版 team-1 / 2026-10-23
この文書はCodexへ渡す制作仕様。ゲーム本体の動作を検証済みとは意味しない。

## 1. 全員で作る体験

「小さな操作を自分で理解して進めると、困っている人を助けられる冒険」。

プレイヤーが最初に見るのは、町民の具体的な困りごと。
スマホの一つの操作に結果があり、確認できた技能が案件の封印を解く。
依頼を終えるとNPCが反応し、装備が手に入り、町の状態が変わる。
次の章で同じ技能を別の条件で使い、成長が自分でも分かる。

制作上の成功を「工程数がそろった」「画面がきれい」「XPが多い」だけで定義しない。
動くこと、意味を理解できること、続きに興味が持てることをそれぞれ確かめる。
公開された開発者インタビューを参考にした本作向けの提案であり、
DQ IVの非公開な社内体制や、面白さを保証する式を再現したものではない。
根拠資料はSOURCES.md。

## 2. 親ディレクター＋8つの専門役

| 役 | 責任と提出物 | 主な変更範囲 |
| --- | --- | --- |
| 親ディレクター | 任務分割、優先順位、仕様の衝突解決、統合、完成の判定 | 作業表、判断記録、共通契約、入口と統合箇所 |
| quest_designer | 依頼の動機、会話、判断、ボスと報酬、町の変化 | 割当済みの章のcontent |
| learning_reviewer | 言葉、1指示1操作、目的、ヒント、技能の確認 | 指摘と改善案。製品編集なし |
| finance_reviewer | 固定例と別計算による独立検算、状態と費用の確認 | 検算表と指摘。製品編集なし |
| engine_engineer | 状態、台帳、計算、保存、実時計、XP、熟練度 | src/core/、割当テスト |
| phone_engineer | フォーム、メール、タブ、復帰、実際らしい操作 | src/phone/、styles/phone.css |
| world_engineer | 地図、人物、ボス、装備、ドット絵、音、反応 | src/world/、styles/game.css、割当assets |
| qa_reviewer | 不具合の再現、境界、差分確認、完走、環境の証跡 | 指摘と検証記録。製品編集なし |
| playtest_analyst | 人間の観察の整理、迷う原因の仮説、改善の比較 | 観察分析。製品編集なし |

親はプロデューサーの進行管理も兼ねる。別の進行管理エージェントを常設しない。
専門役は職能であり、全員を常時動かす必要はない。
通常は親＋最大3子。1つの任務を終えたら回収し、次の必要な役に枠を使う。
役の数・同時数・監視頻度自体を成果指標にしない。
同じエージェントに別の役を順番に任せてもよいが、自己レビューのみで独立検証済みとしない。
ユーザーは方向性と実際に触った感想を返す役。小さな実装判断のたびに呼び出さない。

## 3. 並列作業を始める前の約束

A. 編集の所有権
- 親が任務ごとに編集可能なファイルと編集禁止の範囲を渡す。
- 共通ファイルは単一所有者。別ファイルでも共通のデータ構造を変えるときは親へ戻す。
- 同じ共有作業場所の場合、他担当の未コミット変更を上書きしない。
- worktree等で分ける場合も、統合は親が順番に実施する。無関係な変更を巻き戻さない。
- レビューの対象を版・差分・時刻で固定し、作業途中の別版を同じ合格証跡として混ぜない。

B. 最小の共通契約
CONTRACTS.mdに、操作の入口、state、エラー、ID、教材データ、復帰、共通CSSを記録する。
プログラミング言語の型名は実装側で決めてよい。必要なのは全員が同じ入口を使うこと。
画面の表示値、金融台帳、ボスの判定に別々の真実を持たせない。

C. 製品仕様と制作方法
製品仕様は既存2冊を継続。548標準工程、24追加工程、金融数理、固定XP、
任意の時間特典、報酬ID、保存版、隠しボスの条件を制作都合で変えない。
文言、レイアウト、演出のタイミング、任務の順番は親が合理的に調整する。
範囲・金額・学習目標の変更案が必要なら、理由と影響を判断記録へ残す。
運用文書の版を上げても、ゲームの保存版は自動的には上げない。

## 4. 毎回使う任務票

任務を委譲するときは、次の項目を短く具体化する。

~~~text
任務ID:
担当役:
目的: プレイヤーの何が改善されるか
対象: 章・クエスト・画面・状態
必読資料: ファイルと節
基準の版／前提:
編集可能パス:
編集してはいけないパス:
守る共通契約:
完了条件: 観察・計算できる条件を2〜5個
検証ケース:
返してほしい証跡:
依存先への質問:
~~~

「スマホを全部いい感じに作る」では任務が広すぎる。
例えば「PO-01のメール認証で、別タブへ移って戻っても入力とスクロールが残る」
という単位にし、その動作を確認できる状態まで任せる。

返却する内容:
結論／変更ファイル／受入条件ごとの結果／実行した確認／未確認／残る問題／次の提案。
コマンドを実行していなければ、実行済みの欄へ書かない。
他の役の変更が必要なら、該当ファイルを勝手に直さず変更案を返す。

## 5. 制作フェーズと合格条件

### 準備: 小さな設計確認
親が既存環境と2冊の仕様を読み、quest_designer・learning_reviewer・finance_reviewerへ
独立に読める確認を最大3件委譲する。大規模な再企画会議を始めない。
最初の一周、明らかな理解の障害、固定計算の一覧を回収し、最小契約を決める。

### A: 最初の一周
序章PR-01の12工程と旅人の手帳、PO-01の登録とメール認証を中心に、
町→会話→受注→スマホ→達成→報酬→保存・再開をつなぐ。
手帳は仕様どおり序章の報酬とし、PO-01へ勝手に移さない。
第1章の章ボスやルーペを前倒し付与しない。章の大きな世界変化はBで確認する。
engine／phone／worldを編集範囲を分けて並列化し、親が教材と入口を統合する。

Aで確認すること:
実操作が結果につながる。戻る・別アプリ・再読込で復帰する。
初回XPと装備が一度だけ。最初の目的が画面に示され、必要なヒントが呼べる。
見た目だけのモック、全工程を進める仮ボタンでは合格にしない。
人間観察の材料を渡せる状態にするが、観察を待って無関係な作業を止めない。

### B: 第1章の完成
全77工程、台帳、問い合わせ、交換・受取、5課題の章ボス、ルーペ、町の変化を完成。
この段階で「確認操作がボス攻略につながる」「村人を助けた結果が見える」を一周評価する。
メール、ブラウザー、条件確認、ヒント、途中保存の共通部品を固める。
金融・学習・QAを別観点で確認する。テストが通っていても理解は別途検証する。

### C: 銀行・FX・トレカ
既存の工程を保ち、章単位の小任務で増やす。
各章で固有計算と表示、重要な確認操作、章ボス、装備、復帰を完走してから次へ統合。
KYC再撮影とFX売りの副課題を本体と混同しない。

### D: 暗号資産
第5章の入口と基礎、第6章の現物から出口、ほか3ラボ、運用見送り、経路別ボスを完成。
4ラボすべて実装する。利用者に4ラボ受講を強制しない。
運用見送りの正しい判断でも同じ章の終点へ進める。
出口を終えただけで章ボスを省かない。練習ラボ、ボス、復習の資金を混ぜない。

### E: 全体統合
6章印、隠しボス、8種の装備、全経路の再開、JSON往復、他タブ、
時刻境界、相対URL、モバイルとキーボードを確認し、重要な不具合を直す。
全24クエストの実装状態を数え、未実装を準備中カードで隠さない。
READMEへ起動・確認方法、実施結果、未確認を残す。
A/Bの完成は途中成果であり、全体完成ではない。

## 6. 監視・調整・修正の流れ

常時回り続ける監視スクリプトや、全員参加の会議は初回に作らない。
次の出来事で、必要なレビュー役だけを呼び出す。

| 出来事 | 呼ぶ役 | 親が決めること |
| --- | --- | --- |
| 共通契約・台帳・保存の変更 | engine、QA、必要なら金融 | 影響先と回帰確認 |
| 新クエストの完走 | 学習、金融、QAから必要な役 | 条件・表示・操作の整合 |
| 町・演出・装備の変更 | quest、world、必要なら学習 | 体験方針への適合 |
| 新しい実プレイ観察 | playtest、学習、quest | 原因仮説と次の小さな修正 |
| フェーズ完了 | QA＋必要な専門役 | 証拠と残件を見て統合 |
| 最終納品前 | QA、金融、親 | 重要な残件と確認範囲 |

指摘票:
~~~text
不具合ID:
対象の版・環境:
仕様の根拠:
再現手順:
期待する結果:
実際の結果:
影響:
証跡:
優先度:
修正後に確認する条件:
~~~

重大度の運用:
- Blocker: データ消失、二重送金/報酬、進行不能、必要操作の欠落、金額や条件の重大な誤り。
  該当変更を統合・完了扱いにせず、担当へ修正を返す。無関係な作業は進めてよい。
- Major: 戻れない操作、主要な説明の誤解、狭い画面で操作不可等。対象フェーズの完了前に直す。
- Improvement: 好み、追加演出、任意の磨き込み。親が効果と工数を見て順序を決める。

QAは証拠を示して受入を止められる。好みだけで全体を停止しない。
親は「時間がないから」の一言で重大な指摘を合格へ書き換えない。
原因が違う場合は再現・仕様根拠を確認し、判断と残るリスクを記録する。
同じ原因の修正が2回外れたら、同じパッチの反復をやめ、担当の見方や切分け方法を変える。

## 7. 548工程を遊びにする設計

1操作ずつに分けることと、全操作で大げさなご褒美を出すことは別。
工程は学習の足場。プレイヤーには「今の目的」「少し先の成果」「章の変化」を見せる。

| 長さ | プレイヤーが感じること | 実装するもの |
| --- | --- | --- |
| 1操作 | 押したら何が変わったか分かる | 入力、画面遷移、短いXP表示 |
| 5〜8工程程度の区切り | ここまでできた、中断しても戻れる | 自然な区切りと保存。余分な確認ボタンなし |
| 1クエスト | 自分で一つの用事を解決した | 案件の封印、結果確認、NPCの反応 |
| 1章 | 自分と町が変わった | 条件違いのボス、確定装備、世界変化 |
| 複数章 | 覚えた技能を組み合わせられる | 複合課題と隠しボス、虹誓の大剣 |

振込26工程の例:
「宛先」「金額と手数料」「承認」「受取」の封印が順に解ける。
口座欄を押しただけでは封印が解けない。正しい内容の確認が根拠になる。
送信で終わらず着金を確認したときに村人の用事が完了する。
各工程は小さなXP、封印は短い反応、章ボス後の装備で大きな演出を使う。
この構成は既存の固定XPを変更せず実現できる。

調整する順番:
目的と操作の意味 → 文字と配置 → ヒントと戻り方 → 演出の間隔 → 次の依頼への期待。
タップ数を増やす、連続ログインを要求する、実利益を増やすことを解決策にしない。
初回はガイド付き、条件が変わる課題では自分で確かめ、必要ならヒントを使える。
有効な別経路を受け入れ、指示どおりの最短タップだけを理解の証拠にしない。

XP・難易度の調整案は、期待する体験、現在の計算、変更案、影響範囲をセットで出す。
初期仕様の数値は勝手に変えず、まず表示の間隔と課題の説明で改善する。
「この秒数なら必ずハマる」「ドーパミンが出た」と断言する指標は作らない。

## 8. 検証は3段階で記録する

自動検証: 計算、状態遷移、重複防止、保存、時刻境界等。
ブラウザー確認: 実際の画面、操作、スクロール、戻り、狭い幅、入力と演出の衝突等。
人間プレイ観察: 何に迷い、何を理解し、どこで面倒に感じ、次に何をやりたいか。

この3つは代用できない。AIが「初心者として遊んだ」は観点レビューであり、
実ユーザーの反応や学習効果の実測ではない。
未実施なら観察用の版と手順を準備し、自動検証・実装は継続する。
完成報告では「実装完了／人間観察は未実施」のように分ける。

## 9. 成果の報告

親は節目に、今遊べる範囲、重要な確認結果、残件、次の一手を短く報告する。
監視結果をプレイヤーのゲーム画面へ流し込まない。
作業表とゲームの学習ログ、学習ログと金融台帳を混同しない。
Codexの作業が終わった後も監視が自動継続しているとは説明しない。
必要な自動化を後で作る場合は、起動条件・実行環境・権限・停止方法を別途定義する。
